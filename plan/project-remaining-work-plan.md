# Survyra — Remaining Work, Project-Wide

Verified against actual code (controllers, routes, models, views, JS, `composer.json`, CI config) on 2026-07-23 — not against `task.md`'s checkboxes, which are stale in both directions: several "unchecked" Phase 2 items are actually fully wired, while several Phase 3/4 items with real backend code have **zero UI ever calling them**, which reads as "done" in the code but is invisible/unusable to an actual user. ## 0. Process fix (do this regardless of feature order)

The recurring failure mode across this project isn't missing skill, it's **marking things done before verifying them end-to-end**:
- The Client Analytics Dashboard was treated as shipped with a bug that crashed it on every single load.
- `plan/pending-work-master-plan.md` claimed the Survey Analytics dashboard redesign was done; it was still the old layout.
- `AnalyticsService` shipped three MySQL-only SQL functions that would fail the moment a test actually exercised them.
- Half the items below are backend logic that was genuinely built well, then never connected to a page — which from a "did we finish the ticket" checklist perspective looks done, but isn't usable.

**Fix**: before marking any item below complete, require (a) a real HTTP/tinker walkthrough against seeded data, not just a code review, and (b) `php artisan test` passing, and (c) actually clicking the feature's UI entry point if one is claimed to exist. This is cheap and would have caught every one of the gaps found in this audit.

## 1. Security/correctness bugs — fix first, small blast radius — ✅ ALL FOUR DONE (2026-07-23)

Each item below turned out worse on inspection than the original one-line description — every one of them had at least one additional bug that only surfaced by actually running the code, reinforcing §0's process point. Full test suite went from 154 passing/1 pre-existing failure at the start of this pass to **175 passing / 0 failures** by the end.

1. **2FA is not enforced at login — DONE, and the feature was more broken than described.** Root cause was worse than "never checked": `pragmarx/google2fa` — the package `TwoFactorAuthService` depends on — **wasn't installed at all** (not in `composer.json`, not in `vendor/`). Every 2FA route (setup, confirm, disable, recovery codes) was fatal-erroring, not just unenforced. Fixed by installing the package, then adding real enforcement: `LoginRequest::authenticate()` now logs a 2FA-enabled user back out after password verification and stashes a pending-challenge session key instead of completing login; a new `Auth\TwoFactorChallengeController` + `admin/two-factor-challenge` route/view verify the TOTP or recovery code before `Auth::login()` actually runs. 6 new tests (`tests/Feature/Auth/TwoFactorLoginTest.php`).
2. **File upload question type silently doesn't work — DONE, and it was actually worse: a hard parse error.** `resources/views/survey-questions/file_upload/default.blade.php` had a genuine PHP syntax error (an extra closing paren in the `accept` attribute) that fatal-errored on render — this question type could never even be displayed, let alone silently lose data. Fixed the parse error, then built the real upload pipeline end-to-end: `collectAnswer()` in `survey.js` now returns the actual `File` object and a new shared `postAnswer()` helper posts multipart when needed (3 call sites deduplicated into one); `SurveyResponseController::answer()` passes `$request->file('answer')` through; `ResponseService::saveAnswer()` stores it via a new `storeUpload()` method (private disk, replaces any prior upload for that question, deletes the orphaned old file) and persists a clean JSON reference, never the file object. Added `Response::uploads()` relation, an admin download route (`Admin\ResponseUploadController`), and a download link in the response-detail modal (previously nothing could ever view an uploaded file even in principle). Also found `file_upload`/`image_choice` were never seeded into the `question_types` table (config had 20 types, DB had 18) — re-ran `QuestionTypeSeeder`, and fixed `QuestionTypeRegistryTest`'s stale `toHaveCount(18)` assertion to the real, verified `20`. 3 new tests (`tests/Feature/FileUploadQuestionTest.php`).
3. **Client user roles (editor/viewer) aren't enforced outside team management — DONE.** Added `App\Http\Middleware\EnsureClientCanEdit` (alias `client.can-edit`, checks `ClientUser::isEditor()`) and applied it to every state-changing Portal route: company profile update, API key create/delete, webhook create/delete, Slack integration create/delete, scheduled report create/delete. Read-only routes (dashboard, analytics, listing pages) stay open to viewers, matching what "viewer" should mean. Owner/editor behavior is unchanged. 8 new tests (`tests/Feature/ClientUserRoleEnforcementTest.php`).
4. **Onboarding checklist flags freeze at creation time — DONE, and it was worse: the entire client portal dashboard was fatal-erroring on every load.** `Portal\AnalyticsController::index()` called `$this->onboarding->getChecklist($request->user())` — a method that doesn't exist on `OnboardingService` (only `checklistFor(Client $client)` does, and it takes a `Client`, not the `ClientUser` that was being passed). Every single client-portal dashboard load was crashing. Also found two divergent, half-built onboarding UIs: a broken inline array-shaped block in `portal/analytics/index.blade.php` expecting a shape (`$onboarding['steps'][]['url']`) nothing ever produced, versus an already-correct, self-sufficient partial (`portal/partials/onboarding-checklist.blade.php`) that fetches its own data via the real model methods and was just never wired in. Fixed by deleting the broken inline block in favor of `@include`-ing the working partial, and removing the now-dead `getChecklist()` call and unused `OnboardingService` dependency from the controller. Separately fixed the actual stale-flags bug: `checklistFor()` now uses `updateOrCreate` instead of `firstOrCreate`, recomputing every flag live on each call (all cheap existence checks) instead of freezing them at first creation — `dismissed` (a real user action, not a derived flag) is untouched by this. The unused, never-called `markCompleted()` method was removed as dead code now that recomputation makes it unnecessary. 3 new tests (`tests/Feature/OnboardingChecklistTest.php`), including one asserting the dashboard actually renders (previously would have been impossible to write, since the page always crashed).

## 2. Real backend, zero UI — cheapest wins in the whole roadmap — ✅ ALL FIVE DONE (2026-07-23)

This section's real cost turned out to be almost entirely in verification, not implementation — the "just wire it up" work was genuinely cheap, but four more severe, previously-undetected bugs surfaced purely by executing the wiring against real seeded data instead of trusting that "the route exists and the service has a method" meant it worked. The most serious: **the migration adding 2FA columns, file uploads, and the AI content cache table had never actually been run against the real dev database at all** (only ever applied inside the test suite's auto-migrating SQLite DB) — meaning Bugs 1 and 2 from Section 1, despite passing every Pest test, would have failed instantly against the real running app. Caught only because wiring up the AI panel forced a real end-to-end call against real MySQL.

5. **Real-time analytics polling — DONE.** Wired as a genuine optimization, not just "call it": `analytics.js` now uses the lightweight `/poll` endpoint (server-cached 5s, just a response count) when a specific survey is selected, and only pays for a full dashboard refresh when `has_updates` is true — instead of blindly re-rendering every chart every 30 seconds regardless of whether anything changed. Falls back to the old blind full-refresh when viewing "all surveys" (poll is scoped to one survey). Verified against real seeded data via the actual controller method.
6. **Slack notifications — DONE.** `SendSlackNotificationJob::dispatch()` now fires from the 3 real event sites it was built for: `ResponseService::submit()` (`response_completed` always, `negative_feedback` when sentiment is negative) and `SurveyService::publish()` (`survey_published`). 4 new tests using `Http::fake()`, confirming both that subscribed events actually POST to the configured webhook and that unsubscribed events correctly don't.
7. **AI features — 6 of 7 wired, verified, and one severe bug found and fixed.** Built a real "AI Insights" panel on the Survey Analytics Dashboard (shown when a specific survey is selected) covering Quality Score, Response Summary, Sentiment Analysis, Keywords, Recommended Actions, and Executive Report — each an on-demand button (no auto-run; real AI calls cost money/time), rendering its own result inline. **Found while verifying against real data**: `AiContentCache` had no `$table` override, so Eloquent guessed the pluralized `ai_content_caches`, but the migration created the singular `ai_content_cache` — every single AI method that touches the cache (`summarizeResponses`, `analyzeSentiment`, `extractKeywords`, `recommendedActions`, `generateSurvey`, `suggestQuestions`) threw a table-not-found error on every call. Fixed with an explicit `$table` property; 2 new regression tests. "Suggest Questions" (the 7th capability) deliberately deferred — it belongs in the survey builder page, not the analytics dashboard, and is a distinct, separately-scoped piece of UI work.
8. **AI weekly digest — DONE, and a real send-time bug found.** Scheduled (`weeklyOn(1, '08:00')`). **Found while verifying the actual send**: `WeeklyDigestMail` declared constructor properties named `$from`/`$to` for its date range — these silently collide with `Illuminate\Mail\Mailable`'s own built-in `$from`/`$to` recipient/sender properties, so `Mail::to($user->email)->queue(...)` appeared to work but the real recipient list got overwritten by Carbon date objects, and every digest email failed at send time. Renamed to `$periodFrom`/`$periodTo`; 2 new tests using `Mail::fake()`/`hasTo()` (the specific assertion that would have caught this — `assertSent()` alone would not have, since the bug corrupts the recipient list, not whether the mailable object gets constructed).
9. **Automated backups — DONE, verified with a real backup, not just a config file.** Published `config/backup.php`, tightened the notification email (was hardcoded to `your@example.com`), added `.git`/`storage/framework/{cache,sessions,views}` to the exclude list, scheduled `backup:run`/`backup:clean`/`backup:monitor` daily. Actually ran `backup:run` against the real dev database (not just reviewed the config) — real MySQL dump via `mysqldump`, real zip archive written to disk, verified with `backup:clean` and `backup:monitor` afterward. Along the way, added an optional `DB_DUMP_BINARY_PATH` config knob (`config/database.php`) for environments where `mysqldump` isn't already on `PATH`.

## The single most important finding of this pass

While verifying Section 2's AI panel against real data, `php artisan migrate:status` revealed that **`2026_07_22_000001_add_remaining_phase2_features` — the migration adding 2FA columns, `response_uploads`, `ai_content_cache`, `external_integrations`, `nlp_analyses`, and survey translation columns — had never been run against the real development database.** It only ever existed inside the test suite's auto-migrating SQLite database. This means Section 1's Bug 1 (2FA) and Bug 2 (file upload) fixes, despite every Pest test passing, would have failed instantly against the actually-running application — a fully invisible gap that no amount of test-suite-only verification would have caught.

Running the migration for real then immediately surfaced a second latent bug: `two_factor_secret` was declared as `string` (`varchar(255)`), but `encrypt()`'d values run 300-400+ characters — MySQL correctly rejected every insert, while SQLite's lax type affinity silently let the same oversized value through in every test. Fixed to `text`. **This class of bug (MySQL column-length/type strictness) is structurally invisible to a test suite that only runs on SQLite** — worth flagging as a real, unclosed gap: CI currently only tests against SQLite, so a MySQL-specific regression like this one could ship again undetected. Adding a MySQL service container to the CI matrix would close this permanently; not done in this pass, noted honestly as a follow-up rather than silently left implicit.
